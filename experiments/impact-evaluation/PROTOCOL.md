# 실제 변경·AI 수정 비교 규칙

2026-09-13, 새로운 표본의 kartograph 결과나 AI 수정 결과를 보기 전에 고정한다.
제품 기준은 PR #40의 `bc723c02d100cdb2ec990f5d3d0569e57f67c7e9`다.
초기 개발 표본과 새 평가 표본을 구분하며, 실패한 표본도 결과에서 제거하지 않는다.

## 데이터와 선택

- Kotlin은 [Kotlin SWE-bench](https://github.com/Kotlin/kotlin-swe-bench)의
  `b9025d86f7ae634901396766bd61f6d4ae6d2165`를 사용한다. 해당 tree에는 106개 task가 있다.
- Java는 [Multi-SWE-bench 원본 데이터](https://huggingface.co/datasets/ByteDance-Seed/Multi-SWE-bench)의
  `56ff018c04a38e27ada1e9d0a6d5839a51f88f0d`를 사용한다.
- Java 라이브러리는 Gson·Jackson Core, Kotlin/JVM 도구는 detekt·ktlint, Android 앱은 AnkiDroid로 나눈다.
  외부 서비스 없이 실행하는 라이브러리·개발 도구·앱이라는 서로 다른 사용 맥락을 포함한다.
- 각 저장소에서 full base SHA와 하나 이상의 f2p 기대값이 있는 가장 큰 PR 번호를 선택한다.
  AnkiDroid는 새 표본 두 개를 선택한다. 이미 개발에 사용한 OkHttp #6887·AnkiDroid #19661은 개발 표본이다.
- 새 기본 표본은 Gson #1555, Jackson Core #1309, detekt #7888, ktlint #2983,
  AnkiDroid #20250·#19982다. ID·원본 SHA·데이터 지문은 [cohort.json](cohort.json)에 기록한다.
  f2p가 없는 최신 항목을 제외한 이유도 기록한다. 이는 실패 재현 기반 평가의 자격 조건이다.
- 원본 빌드 환경을 재현할 수 없을 때만 같은 고정 데이터에서 다음으로 큰 적격 PR을 예비 표본으로 활성화한다.
  저장소당 최대 한 개이며 AnkiDroid 두 표본은 이 예비 한도를 공유한다. 원래 표본의 실행 실패는 계속 공개한다.
  그래프 누락, 많은 후보, AI 실패, 시간·비용 열세를 이유로 표본을 교체하지 않는다.

## 테스트 출처와 실제 변경

원래 source, 동일한 회귀 test patch를 적용한 buggy 상태, gold source fix 후 상태를 별도로 보관한다.
외부 prepare/test 스크립트는 지시가 아닌 자료로 읽고 검토한 native 명령으로 재현한다.
환경 변경이 필요하면 source/test 변경과 분리해 기록한다. 공식 Docker 벤치마크 점수라고 부르지 않는다.

원래 저장소의 테스트와 벤치마크가 추가·수정한 테스트를 파일/선언 출처와 내용 지문으로 구분한다.
**수정 전 예측은 test patch를 주입하지 않은 원래 그래프**로 평가한다. 이후 추가된 테스트를
원래부터 존재한 실패 예측 대상으로 세지 않는다. 주입 oracle의 그래프 결과는 별도 측정이다.
JUnit XML 등의 실제 실행에서 실패→통과 전이를 확인하고, 동적 display name의 JVM 연결이
불확실하면 미해결로 남긴다. 실행한 oracle은 관찰된 영향의 하한이며 precision의 전체 정답이 아니다.

동일한 원본과 실제 변경에 대해 선택한 대상의 포함·누락·미해결, 후보 수·파일 수·출력량,
source 빌드·snapshot capture·질의 시간을 각각 기록한다. 같은 테스트를 전부 실행하는 비용과
소스 검색·읽기 작업도 비교한다. 테스트 생략은 수행하거나 권장하지 않는다.

## AI 비교

두 조건 모두 같은 원래 저장소, 문제 설명, 공개된 기존 테스트와 read/search/list/replace/test/refresh 도구를 받는다.
수정은 명시된 production 파일만 허용한다. 일반 shell이나 임의 명령을 제공하지 않는 제한된 실제 수정 실험이다.
실험 조건만 kartograph 스킬과 공통 CLI를 호출하는 impact 도구를 받는다.

새 회귀 test patch·gold fix·정답 변경 파일 목록·oracle 결과는 AI workspace/입력/그래프에 넣지 않는다.
Multi-SWE-bench의 별도 `hints`처럼 fix/test patch에서 만든 추가 힌트도 제외한다.
기존 공개 테스트가 실패를 드러내면 양쪽 모두 동일하게 볼 수 있다. 이것과 숨긴 회귀 테스트를 구분한다.
입력은 매 요청마다 packet-ask로 정제하고, 모델은 저장소 밖의 임시 디렉터리에서 도구 없이 실행한다.
실제 읽기·수정·빌드·테스트는 로컬 controller가 허용 목록과 고정 argv로 수행한다.

- 모델: 동일한 Claude Opus 5 계열의 고정 식별자, low effort. 실제 응답의 모델 ID도 대조한다.
- 조건당 2회, 반복 1은 source→impact, 반복 2는 impact→source 순서다. 각 trial은 새 상태에서 시작한다.
- trial당 900초, 도구 시도 12회, 모델 요청 최대 13회. 도구 응답은 동일한 12,000자 기본 한도로 제한한다.
  잘림과 실패를 명시하며 invalid 요청도 예산을 소비한다. 모델 호출·도구·컴파일 시간 모두 trial 시간에 포함한다.
- 공개 source를 동일하게 빌드한 workspace에서 시작한다. 공통 빌드와 실험 조건의 추가 capture 비용을 별도로 기록하고,
  준비 비용을 포함한 총시간도 제공한다. 저장 그래프 재사용을 증분 빌드라고 부르지 않는다.
- 수정 후 그래프는 stale이다. 다시 사용하는 경우 성공한 compile/capture와 내용 지문 검사를 거친다.
  내용 지문 일치를 빌드 provenance 증명으로 승격하지 않는다.

AI 종료 후 독립된 grader에 허용된 source 변경만 적용하고 숨긴 oracle과 기존 테스트를 실행한다.
AI의 성공 주장, 종료 코드 하나, 테스트 파일 수정으로 성공 처리하지 않는다. 모델·도구 실패, 예산 소진,
컴파일 실패, oracle 실패, 기존 테스트 회귀를 각각 기록한다. 시간·읽은 파일/문자·token/cache 사용량·제공자가
보고한 비용을 수집한다. 비용 정보가 없으면 unknown이며 0으로 만들지 않는다.

## 채점과 개선 규칙

우선순위는 실제 수정 성공과 회귀 방지이며, 동등한 성공 조건에서 검토량·시간·비용을 비교한다.
도구 호출 수만 줄었다고 생산성 향상으로 결론 내리지 않는다. 기존 입력·원래 oracle을 보존하고
동일한 모델/예산의 paired 결과, 개별 실패와 전체 표본 결과를 함께 공개한다.

구체적인 실익은 독립적인 새 사례 두 개 이상에서 반복되어야 한다. 예를 들어 같은 oracle 성공과
회귀 없음 아래 시간 또는 제공자 보고 비용이 두 반복에서 일관되게 줄어드는지 확인한다.
이 작은 표본으로 통계적 우위나 모든 프로젝트의 성능을 주장하지 않는다.

실익이 재현되지 않거나 회귀가 있으면 원인을 조사해 제품/도구 인터페이스를 개선한다.
이미 결과를 본 표본은 개발 표본으로 전환하고, 같은 사전 선택 규칙의 다음 미실행 표본을 새 검증 표본으로
고정한다. 원래 결과를 지우거나 유리한 반복만 남기지 않는다. harness 결함 수정도 버전과 영향을 기록한다.

전체 CI의 자동 갱신·cache 총비용과 최종 배포본 설치는 후속 단계에서 별도로 검증한다.
